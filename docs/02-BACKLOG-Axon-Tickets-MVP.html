Epic 1 — Event Setup and Ticket Configuration

Goal: Organizers can create and configure events with tiers, payment QR, venue details, and capacity settings before going live.
E1-F01[F]P0SP 3✓ SHIPPED
Create a new event
As an organizer, I want to create a new event with title, description, venue, date/time, and capacity so that attendees can register.
Acceptance Criteria:
  • Form fields: title (required), description (optional), venue (required), address (required), city (required), starts_at (required), ends_at (optional), max capacity per event (required), max group size (default 10, configurable).
  • Event is created with status draft; only published events are visible to public.
  • Event slug is auto-generated from title and is unique.
  • Conference-specific fields available: speaker name, agenda items, sponsors, FAQs.
  • Admin sees success confirmation with link to event detail page.
E1-F02[F]P0SP 3
Upload event payment QR
As an organizer, I want to upload one or more payment QR images (GCash/Bank) per event so that attendees know exactly where to send payment.
Acceptance Criteria:
  • Admin can upload 1–3 payment QR images per event (JPEG/PNG, max 2MB each).
  • Each QR has an optional label (e.g., "GCash", "BDO Bank Transfer").
  • Optional payment text instructions field (account name, account number) stored alongside QR.
  • Payment QR is displayed on the attendee payment instruction screen.
  • QR images stored in Cloudinary under a private event-specific folder.
E1-F03[F]P0SP 2
Add venue map link
As an organizer, I want to add a Google Maps URL to the event so that attendees can easily navigate to the venue.
Acceptance Criteria:
  • Admin can enter a venueMapUrl when creating or editing an event.
  • URL is validated as a valid HTTP/HTTPS URL.
  • Displayed on event detail page as "Get Directions" link (opens in new tab on mobile).
  • Included in QR confirmation email.
E1-F04[F]P0SP 3
Create ticket tiers (Early Bird, Solo, Group)
As an organizer, I want to create ticket tiers with pricing, availability dates, and capacity so that attendees see the right options at the right time.
Acceptance Criteria:
  • Each tier has: name, description, price (PHP), total quantity, max per registration (solo: 1, group: N), sale_starts_at, sale_ends_at, is_visible.
  • Tiers are displayed on the event page in sort order.
  • Tiers outside their sale window are greyed out or hidden (configurable per tier).
  • Early Bird tier: when saleEndsAt passes and registration is still draft, registration is auto-cancelled (see E2-F09).
  • Admin can edit or delete tiers (delete only when no registrations linked).
E1-F05[F]P1SP 2
Set event status (draft / published / on_sale / cancelled)
As an organizer, I want to control the publish status of an event so that it is only visible when I'm ready.
Acceptance Criteria:
  • Admin can change event status: draft → published → on_sale → completed / cancelled.
  • Only on_sale events show the registration CTA to attendees.
  • sold_out is auto-set when all tier capacity is consumed.
  • cancelled displays a cancellation notice on the public page.
E1-F06[F]P2SP 2
Configure max group size per event
As an organizer, I want to set the maximum number of attendees allowed per bundle registration so that I can control group sizes for different events.
Acceptance Criteria:
  • Admin sets maxGroupSize field on event (integer, min 2, max 50, default 10).
  • Displayed in admin event detail for quick reference.
  • Enforced on registration API — group with more attendees than limit returns 400.
  • Registration form shows maximum group size to attendees.

Epic 2 — Attendee Registration

Goal: Attendees can register solo or as a group with minimal friction, receive a confirmation, and access their registration using email + reference number.
E2-F01[F]P0SP 5✓ SHIPPED
Solo registration with required fields
As an attendee, I want to register for an event by providing my name, email, and contact number so that I can secure my spot.
Acceptance Criteria:
  • Required fields: first name, last name, email, contact number.
  • Optional fields (collapsible section): gender, age, country, company, affiliation, city.
  • Submit button disabled until all required fields are valid.
  • Inline validation errors shown per field (not just on submit).
  • On success: registration created with status draft, reference number generated, confirmation email sent, attendee redirected to confirmation page.
E2-F02[F]P0SP 8✓ SHIPPED
Group / bundle registration
As a group coordinator, I want to register multiple attendees under one registration so that I can pay once and each person receives their own QR code.
Acceptance Criteria:
  • "Are you registering for others?" toggle on registration form.
  • When toggled on: additional attendee rows appear (each: first name, last name, email, contact number — all required).
  • Add/remove attendee row buttons (up to event's maxGroupSize).
  • Maximum attendees enforced and displayed ("Max X attendees per registration").
  • Each attendee email checked for duplicates against the current event independently.
  • One registration record created with type group; N individual Attendee records created.
  • Each attendee's QR is sent to their individual email on approval.
  • Lead registrant sees all attendee names on the confirmation page.
E2-F03[F]P0SP 3
Duplicate email prevention
As an attendee, I want to see a clear error if my email is already registered so that I don't accidentally create duplicate registrations.
Acceptance Criteria:
  • Duplicate check: per-event, per-email, on non-cancelled registrations.
  • Error message: "This email is already registered for this event. If you believe this is an error, contact the organizer."
  • Error shown inline on the email field (not just toast).
  • For group registration: each attendee email is individually checked; specific row highlighted with error.
  • API returns HTTP 409 Conflict for duplicates.
E2-F04[F]P0SP 3
Registration confirmation screen
As an attendee, I want to see a confirmation page after registering so that I know my registration was received and understand what to do next.
Acceptance Criteria:
  • Confirmation page at /register/confirm/[registrationId].
  • Displays: registration reference number, all attendee names, selected tier, status "Pending Payment".
  • Next step shown clearly: "Upload your proof of payment to complete your registration."
  • Link to payment instruction page.
  • Message: "A confirmation email with your reference number has been sent to [email]."
  • Page accessible via email + reference number (no account required).
E2-F05[F]P0SP 3
Attendee status access (email + reference login)
As an attendee, I want to look up my registration using my email and reference number so that I can check my status without creating an account.
Acceptance Criteria:
  • Lookup page at /my-registration — input email + reference number.
  • Returns the matching registration if both credentials match.
  • Session token issued (JWT, 24-hour TTL) for continued access.
  • Attendee can see: status, attendee names, tier, proof upload status, rejection reason (if rejected).
  • Invalid credentials return: "No matching registration found. Check your email or reference number."
E2-F06[F]P1SP 3
Optional profile completion
As an attendee who has accessed my registration, I want to optionally set up a password and complete my profile so that I can log in more easily in the future.
Acceptance Criteria:
  • "Complete your profile" card visible on registration page after accessing via reference number.
  • Optional fields: password (creates account), gender, age, country, company, affiliation, city.
  • Setting a password enables standard email/password login in future sessions.
  • Profile completion is not required to view status, upload proof, or receive QR.
E2-F07[F]P1SP 2
Tier selection before registration
As an attendee, I want to select a ticket tier before filling in the registration form so that I know the price and whether the tier is available.
Acceptance Criteria:
  • Event detail page shows available tiers with price, availability window badge (e.g., "Early Bird — Ends June 14"), and remaining capacity.
  • Sold-out tiers are greyed out with "Sold Out" label (not clickable).
  • Tiers outside sale window are greyed with "Available [date]" or "Closed" label.
  • Selecting a tier carries the selection to the registration form.
E2-F08[F]P0SP 2
Registration confirmation email
As an attendee, I want to receive a confirmation email immediately after registering so that I have my reference number saved even if I close the browser.
Acceptance Criteria:
  • Email sent to lead registrant email immediately on registration creation.
  • Email contains: event name, reference number, attendee names, tier, payment instruction link, registration status page link.
  • Email sent via Resend with custom domain from address.
  • Email failure is logged; admin can trigger resend.
E2-F09[F]P1SP 3
Early Bird auto-cancellation of draft registrations
As the platform, I want to automatically cancel draft registrations when the Early Bird tier sale window closes so that capacity is freed and attendees are notified.
Acceptance Criteria:
  • Scheduled job runs daily (configurable) at tier saleEndsAt.
  • Finds all registrations in draft status for expired tiers.
  • Transitions each to cancelled.
  • Cancellation email sent: "Your Early Bird registration (Ref: AXN-...) has been cancelled as the registration window has closed."
  • Action written to Audit Log.

Epic 3 — Manual Payment Proof Submission

Goal: Attendees can see payment instructions, pay manually, upload proof, and receive clear status feedback — all within the platform.
E3-F01[F]P0SP 3
Payment instruction screen
As an attendee, I want to see clear payment instructions and the organizer's payment QR so that I know exactly how much to pay and where.
Acceptance Criteria:
  • Payment screen shows: amount to pay (based on tier × attendee count), payment QR image(s), payment method labels, reference to include in payment description (registration reference number).
  • If multiple payment QRs exist: displayed as tabs or cards (e.g., "GCash" | "Bank Transfer").
  • Accessible at: /events/[slug]/payment/[registrationId].
  • Payment screen accessible without account (via reference number session).
  • "Upload Proof of Payment" button prominently displayed below payment details.
E3-F02[F]P0SP 5✓ SHIPPED
Upload proof of payment
As an attendee, I want to upload a screenshot of my payment proof so that the organizer can verify my payment.
Acceptance Criteria:
  • File picker supports JPEG, PNG, PDF (max 5MB).
  • Drag-and-drop supported on desktop.
  • Client-side: file type and size pre-validated before upload.
  • Server-side: MIME type validated against file magic bytes.
  • Upload progress indicator shown during upload.
  • On success: file thumbnail shown, registration status moves to submitted, confirmation message: "Your proof has been submitted. We'll notify you once verified."
  • On failure: clear error with reason (wrong type, too large, network error).
  • File stored in private Cloudinary folder (not publicly accessible).
  • Submit button disabled until file is selected and valid.
E3-F03[F]P0SP 3
Re-upload proof after rejection
As an attendee whose proof was rejected, I want to upload a new proof so that I can correct the issue and get my registration approved.
Acceptance Criteria:
  • When registration status is rejected, the status page shows rejection reason and an "Upload New Proof" button.
  • Re-upload creates a new PaymentProof record (original is retained in audit trail).
  • Status transitions back to submitted on re-upload.
  • Re-upload notification sent to organizer's verification queue.
  • Re-upload action logged in Audit Log.
E3-F04[F]P1SP 2
Prevent duplicate proof submission
As an attendee, I want the system to prevent me from accidentally submitting multiple proofs for the same registration so that I don't create confusion for the organizer.
Acceptance Criteria:
  • If registration has an active PaymentProof in submitted or pending_verification status: upload button is hidden, message shown: "Proof already submitted. Awaiting verification."
  • Upload is only available when: no proof exists (draft) or last proof was rejected.
  • API returns 409 if proof is submitted for a registration not in an uploadable state.
E3-F05[F]P1SP 2
Registration status page
As an attendee, I want to see the current status of my registration at any time so that I know where I am in the process.
Acceptance Criteria:
  • Status page at /my-registration/[referenceNumber] accessible via email + reference credentials.
  • Shows: current status (with icon), tier, attendee names, event details, last updated timestamp.
  • Progress indicator: Draft → Submitted → Verified → QR Sent (visual step bar).
  • If rejected: rejection reason displayed with re-upload CTA.
  • If approved: "QR sent to your email" confirmation with event date reminder.

Epic 4 — Organizer Verification Workflow

Goal: Organizer can efficiently review, approve, or reject payment proofs with minimal clicks, full context, and a complete audit trail.
E4-F01[F]P0SP 5
Pending verification queue
As an organizer, I want to see a list of all submitted payment proofs awaiting review so that I can work through them efficiently.
Acceptance Criteria:
  • Admin page at /admin/verifications.
  • Default tab: "Pending" (status: submitted or pending_verification), sorted oldest first.
  • Tabs: Pending | Approved | Rejected | All.
  • Each row: reference number, lead name, tier, registration type (Solo/Group), attendee count, submission time, proof thumbnail.
  • Click row → verification detail page.
  • Pagination: 20 per page.
  • Count badge on Pending tab (refreshes every 60s).
E4-F02[F]P0SP 5
Proof preview and attendee details
As an organizer, I want to see the full proof image and complete attendee details on the verification page so that I have all the context needed to make a decision.
Acceptance Criteria:
  • Left panel: full-size proof image (served via Cloudinary signed URL, 30-min expiry).
  • Right panel: reference number, tier, amount due, all attendee names, lead email, registration date, submission date.
  • Group registrations: expandable list of all N attendees with their emails.
  • Proof image never served via public URL — always signed.
  • Image loads in < 2 seconds via Cloudinary CDN.
E4-F03[F]P0SP 5✓ SHIPPED
Approve registration
As an organizer, I want to approve a payment proof with a single click so that QR codes are automatically generated and emailed to all attendees.
Acceptance Criteria:
  • Approve button on queue row and detail page.
  • Confirmation modal: "Approve this registration and send QR codes to [N] attendee(s)?"
  • On confirm: status → approved; N QR tokens generated; N emails dispatched; action written to Audit Log.
  • Success toast: "Registration approved. QR codes sent to [N] attendee(s)."
  • Row removed from Pending tab; moved to Approved tab.
  • If email delivery fails: error logged, admin sees "Resend QR" option.
E4-F04[F]P0SP 5
Reject registration with reason
As an organizer, I want to reject a payment proof with a reason so that the attendee knows what to fix and can re-upload.
Acceptance Criteria:
  • Reject button opens a modal with reason selector.
  • Preset reasons: "Incorrect amount", "Blurry / unreadable image", "Wrong reference included", "Duplicate payment proof", "Payment appears cancelled", "Other (specify)".
  • If "Other": free-text field required (max 300 chars).
  • On confirm: status → rejected; rejection reason stored; rejection email sent; Audit Log written.
  • Row moved to Rejected tab. Reason visible in detail view.
  • Attendee receives email with reason and re-upload link.
E4-F05[F]P1SP 3
Bulk approve registrations
As an organizer, I want to select and approve multiple registrations at once so that I can process a batch of valid proofs quickly.
Acceptance Criteria:
  • Checkbox on each queue row; "Select All" checkbox in header.
  • Bulk Approve button appears when 2+ rows selected (max 20 per action).
  • Confirmation dialog lists all selected registration references.
  • Each approved individually (no all-or-nothing) — failures flagged without blocking successes.
  • Summary after bulk: "X approved, Y failed (see details)".
E4-F06[F]P0SP 3
Audit trail for organizer actions
As an organizer, I want every action I take to be recorded in an audit log so that I have a full history for accountability and troubleshooting.
Acceptance Criteria:
  • Audit log page at /admin/audit.
  • Logged actions: create event, update event, approve registration, reject registration, resend QR, check-in override, bulk approve, export CSV.
  • Each log entry: admin ID, action, entity type/ID, metadata (reason, count, etc.), timestamp.
  • Filterable by action type and date range.
  • Audit log is read-only (no delete or edit).
E4-F07[F]P1SP 2
Resend QR from admin
As an organizer, I want to resend QR codes for an approved registration so that I can help attendees who didn't receive their email.
Acceptance Criteria:
  • "Resend QR" button on approved registration detail page.
  • Resends QR emails to all N attendees in the registration.
  • Success toast: "QR codes resent to [N] attendee(s)."
  • Action written to Audit Log.

Epic 5 — QR Generation and Email Delivery

Goal: Each attendee receives an individual, secure QR code via email within minutes of organizer approval.
E5-F01[F]P0SP 5✓ SHIPPED
Generate 1 QR per attendee on approval
As the system, I want to generate a unique QR code for each attendee in a registration when the organizer approves it so that each person has their individual check-in credential.
Acceptance Criteria:
  • N QR tokens generated (N = number of attendees in registration) on approval action.
  • Each QR token: UUID v4 (or HMAC-signed opaque string) — no PII in payload.
  • QR token stored on the Attendee record.
  • QR image rendered as PNG using qrcode npm package.
  • Tokens are unique globally (enforced by DB unique constraint).
E5-F02[F]P0SP 5✓ SHIPPED
Styled HTML QR email to each attendee
As an attendee, I want to receive a well-formatted email with my QR code so that I can easily find and present it on event day.
Acceptance Criteria:
  • Email sent to each attendee's individual email address (not lead-only).
  • Email contains: attendee name, event title, event date/time, venue name, Google Maps link, tier name, registration reference, QR code image embedded.
  • HTML email renders correctly in Gmail (mobile + desktop) and Outlook.
  • QR image is embedded as base64 or hosted on Cloudinary CDN (not attached as file).
  • Email subject: "Your ticket for [Event Name] — [Reference]"
  • From address: configured custom domain (e.g., hello@axontickets.ph).
E5-F03[F]P0SP 3
Rejection email with reason
As an attendee whose proof was rejected, I want to receive an email with the rejection reason and a link to re-upload so that I can fix the issue.
Acceptance Criteria:
  • Rejection email sent to lead registrant email.
  • Email contains: event name, reference number, rejection reason, link to /my-registration/[ref] to re-upload.
  • Email subject: "Action Required — Payment Proof Update Needed for [Event Name]"
  • Tone: professional, clear, non-alarming.
E5-F04[F]P1SP 2
Invalid / used QR handling
As a check-in staff member, I want to see a clear error when scanning an invalid or already-used QR so that I can handle the situation correctly.
Acceptance Criteria:
  • Unknown QR token → "Invalid QR code. Not found in system."
  • QR from non-approved registration → "Registration not verified. Contact organizer."
  • Already checked-in → "Already checked in at [time]. Attendee: [name]."
  • All three cases handled gracefully — no 500 errors displayed.

Epic 6 — Attendance Check-in

Goal: Event-day check-in is fast, reliable, and works on mobile browsers with camera access.
E6-F01[F]P1SP 5✓ SHIPPED
Browser camera QR scanner
As check-in staff, I want to use my phone's camera to scan attendee QR codes so that check-in is fast and hands-free.
Acceptance Criteria:
  • Camera scan using @zxing/browser library on /admin/checkin.
  • Camera access requested via browser permission API (works on Chrome/Safari mobile).
  • Scanner renders full-screen on mobile (max-width 480px layout).
  • Successful scan triggers check-in API and shows full-screen result within 500ms.
  • Result card: attendee name (large text), tier, event, check-in time, green/red status.
  • Scanner auto-resets 3 seconds after result for next attendee.
  • Camera-denied fallback: shows text input field.
E6-F02[F]P1SP 2
Manual attendee lookup fallback
As check-in staff, I want to search for an attendee by name or email when they arrive without their QR so that no one is turned away due to a technical issue.
Acceptance Criteria:
  • Search field on check-in page (below scanner or on separate tab).
  • Search by: first name, last name, or email (partial match, case-insensitive).
  • Results show: name, tier, registration status, check-in status.
  • Manually mark as checked-in from search result.
  • Manual check-in logged as "manual" in check-in record.
E6-F03[F]P1SP 2
Duplicate check-in prevention
As check-in staff, I want the system to prevent the same QR from being scanned twice so that attendees can't check in multiple times.
Acceptance Criteria:
  • If attendee already checked in: returns "Already checked in at [time]" — does NOT create a second check-in record.
  • Check-in record stores: attendee ID, checked-in timestamp, method (scan/manual), check-in-by admin ID.
  • Only approved attendees can be checked in; others return "Registration not verified."

Epic 7 — Basic Analytics

Goal: Organizer has a real-time overview of registrations, revenue, and event-day attendance.
E7-F01[F]P1SP 3
Analytics dashboard with key metrics
As an organizer, I want a dashboard showing key registration metrics so that I can monitor event health at a glance.
Acceptance Criteria:
  • Metrics: total registrations, by-status breakdown, by-tier breakdown, checked-in count, capacity progress.
  • Revenue estimate: sum of (approved registrations × tier price) — labelled as "estimate".
  • Capacity progress bar: per tier and overall (approved / total capacity %).
  • Auto-refreshes every 60 seconds.
  • Filterable by event (for multi-event platform).
E7-F02[F]P2SP 2
Capacity progress on public event page
As an attendee viewing an event, I want to see how many spots remain so that I know if I need to register soon.
Acceptance Criteria:
  • Capacity bar shown per tier on event detail page (approved count / total capacity).
  • Updates on each page load (SSR revalidation).
  • Does not expose exact approved count — shows "X% filled" or "Limited spots remaining."

Epic 8 — Future-Ready Data Foundation

Goal: Capture behavioral data silently (no UI) to enable future analytics, marketing, and recommendations.
E8-F01[F]P3SP 2
Log event page views
As the platform, I want to record every event page view so that we can analyze event discovery patterns in the future.
Acceptance Criteria:
  • Server-side: EventView record created on each event page load (eventId, anonymous sessionId, timestamp).
  • No UI exposed. No cookie or tracking consent required (anonymous, no PII).
  • Table indexed on eventId, createdAt.
E8-F02[F]P3SP 1
Log registration funnel steps
As the platform, I want to record registration funnel events (form opened, tier selected, submitted) so that we can analyze conversion in the future.
Acceptance Criteria:
  • Log: registration_started, tier_selected, registration_submitted, proof_uploaded — each with eventId and sessionId.
  • No UI exposed. No PII stored at this point (only after registration is created).

Epic 9 — Platform Infrastructure & Technical Stories

Goal: Data model, API endpoints, services, and infrastructure that support all functional epics.
E9-T01[T]P0SP 5✓ SHIPPED
Database migration: Registration, Attendee, PaymentProof, AuditLog, EventView
As a developer, I want the new Prisma models and enum values to be migrated to the production database so that the application can store registration and proof data.
Acceptance Criteria:
  • New models: Registration, Attendee, PaymentProof, AuditLog, EventView.
  • New enum: RegistrationStatus (draft, submitted, pending_verification, approved, rejected, cancelled).
  • Event model additions: paymentInstructions, paymentQrImages (JSON), venueMapUrl, maxGroupSize.
  • npx prisma migrate dev completes without errors.
  • All existing tables and data preserved (additive migration only).
  • Indexes: Registration(eventId, status), Attendee(registrationId), Attendee(eventId, email), PaymentProof(registrationId).
E9-T02[T]P0SP 8
API: POST /registrations (solo and group)
As a developer, I want a POST endpoint that creates a registration with attendees so that the frontend can submit both solo and group registrations.
Acceptance Criteria:
  • Endpoint: POST /api/v1/registrations. No JWT required for creation.
  • Body: { eventId, tierId, registrationType, leadAttendee: {...}, additionalAttendees?: [...] }.
  • Validates: all required fields, event/tier exists and is on sale, duplicate emails per event, group size <= maxGroupSize, tier capacity not exceeded.
  • DB transaction: Registration + N Attendee records created atomically.
  • Returns: registration ID, reference number, status.
  • Triggers: confirmation email to lead attendee.
  • Rate limit: 10 requests/minute per IP.
E9-T03[T]P0SP 5
API: POST /registrations/:id/proof (proof upload)
As a developer, I want a proof upload endpoint that stores files securely and transitions registration status so that the organizer can review them.
Acceptance Criteria:
  • Endpoint: POST /api/v1/registrations/:id/proof. Auth: reference session or attendee JWT.
  • MIME validation against file magic bytes (server-side). Accepts: image/jpeg, image/png, application/pdf.
  • Max size: 5MB enforced server-side.
  • File uploaded to Cloudinary private folder: axon-tickets/payment-proofs/private/[registrationId].
  • IDOR guard: registration must belong to authenticated session.
  • Status machine: only accepts upload when status is draft or rejected.
  • Returns: proof ID, status (submitted).
E9-T04[T]P0SP 5
API: PATCH /admin/verifications/:id/approve
As a developer, I want an admin endpoint that approves a registration, generates QR tokens, and triggers email delivery so that the approval action is atomic and reliable.
Acceptance Criteria:
  • Endpoint: PATCH /api/v1/admin/verifications/:id/approve. Auth: admin JWT.
  • Transaction: status → approved; N QR tokens generated and stored on Attendee records; AuditLog written.
  • Post-transaction: email dispatch (async — email failure does not roll back DB).
  • Returns: registration ID, attendee count, email dispatch status.
E9-T05[T]P0SP 3
API: PATCH /admin/verifications/:id/reject
As a developer, I want an admin endpoint that rejects a registration with a reason, stores it, and triggers the rejection email.
Acceptance Criteria:
  • Endpoint: PATCH /api/v1/admin/verifications/:id/reject. Auth: admin JWT.
  • Body: { reason: string, note?: string }. Reason must be one of the approved preset values or "other".
  • Status → rejected; reason stored on PaymentProof; AuditLog written.
  • Rejection email dispatched to lead registrant.
E9-T06[T]P0SP 3
API: GET /registrations/lookup (email + reference)
As a developer, I want an endpoint that authenticates an attendee by email + reference number and returns a session token so that attendees can access their registration without an account.
Acceptance Criteria:
  • Endpoint: POST /api/v1/registrations/lookup. No prior auth required.
  • Body: { email, referenceNumber }.
  • Returns: session JWT (24h TTL) + registration summary if credentials match.
  • On mismatch: HTTP 404 — "No matching registration found."
  • Rate limit: 10 attempts/minute per IP to prevent brute-force on reference numbers.
E9-T07[T]P0SP 3
Extract EmailService as shared module
As a developer, I want email sending logic extracted into a shared EmailService module so that all email types (confirmation, QR, rejection) are sent consistently.
Acceptance Criteria:
  • New EmailModule with EmailService.
  • Methods: sendRegistrationConfirmation(), sendQrDelivery(), sendRejectionNotice(), sendCancellationNotice().

As a security requirement, file uploads must be validated by content (not extension) so that disguised malicious files are rejected.
Acceptance Criteria:
  • Server reads first 8 bytes of uploaded file to determine MIME type.
  • Accepts: FFD8FF (JPEG), 89504E47 (PNG), 25504446 (PDF).
