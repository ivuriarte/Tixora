1. Test Strategy Overview

The Axon Tickets test strategy follows the testing pyramid: many fast unit tests at the base, integration tests in the middle, and fewer but critical E2E tests at the top. Security tests run as a separate dedicated phase before any production deployment.

LayerToolCount Target (MVP)SpeedWhen Run
UnitJest (API), Vitest (Web utils)40–50 testsFast (<2s total)Every commit (CI)
IntegrationJest + supertest + test DB30–40 testsMedium (10–30s)Every PR + pre-deploy
E2EPlaywright10–12 scenariosSlow (2–5 min)Pre-deploy + manual QA
SecurityJest + manual + curl scripts18+ checksMediumAfter Phase 3, 4, 6 + pre-production
UATManual (organizer + tester)5 scenariosManualFinal QA before launch

Test Environments

  • Unit: In-memory, no external services. All DB and services mocked.
  • Integration: Dedicated test PostgreSQL database (Neon branch). Redis test instance. Resend in dry-run mode (log-only, no actual emails sent). Cloudinary — mocked service layer.
  • E2E: Staging environment (Vercel preview deploy) connected to staging DB and staging Cloudinary folder.
  • UAT: Staging environment. Real emails sent to test accounts.

8. Edge Cases

IDEdge CaseExpected Behavior
EC-01Two concurrent requests to register with same email for same event (race condition)Only one succeeds (201). Second gets 409. DB unique constraint on (eventId, email) as safety net.
EC-02Group registration where one attendee's email matches an already-registered attendeeEntire registration rejected with 409. Partial group insertion not permitted.
EC-03Admin approves registration but email delivery fails (Resend timeout)Registration status set to APPROVED (persisted). Email failure logged as structured error. Admin can trigger resend manually. DB is source of truth — not the email.
EC-04Attendee uploads proof when their registration is in DRAFT state (no prior proof)Proof accepted. Status transitions DRAFT → SUBMITTED.
EC-05Attendee uploads proof when registration is in APPROVED stateHTTP 422. Message: "Registration already approved."
EC-06Duplicate QR scan within 1 second (double-tap scenario)Both requests processed. Second returns 200 with "already checked in" message. No duplicate DB write (idempotent check-in).
EC-07Early bird tier sale ends during a DRAFT registration (attendee fills form but delays upload)Tier's saleEndsAt enforced at proof upload time. If sale ended: 422 "Early bird registration period has ended."
EC-08Admin cancels event that has APPROVED registrationsAll APPROVED registrations transition to CANCELLED. Cancellation emails sent to all lead registrants. Audit log has one CANCEL_EVENT entry.
EC-09Re-upload after rejection replaces previous proof (not appends)New ProofProof record created. Status returns to SUBMITTED. Previous proof record retained in DB (immutable history) but not active for review.
EC-10Group registration where lead email is same as one of the additional attendees' emails400 "All attendee emails within a group must be unique."
EC-11Manual check-in of attendee whose registration is REJECTED403 "Cannot check in. Registration status is REJECTED."
EC-12Attendee session JWT used after registration is CANCELLEDJWT still validates (token-based), but any action returns 422 "Registration has been cancelled."

10. CI/CD Integration

CI Pipeline (GitHub Actions)

  1. Lint: eslint + tsc --noEmit (fail fast on type errors)
  2. Unit tests: jest --testPathPattern spec (API) + vitest run (packages)
  3. Integration tests: Spin up Neon test branch → run integration suite → teardown
  4. npm audit: npm audit --audit-level=high — fail if critical/high found
  5. Build: turbo build
  6. E2E (pre-deploy only): Playwright against Vercel preview URL — runs on PR merge to main
Test Gate: No code can merge to main without passing unit + integration + lint. E2E runs post-merge on preview before promotion to production.
