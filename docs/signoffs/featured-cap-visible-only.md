# Gate Ledger — Homepage featured cap counts only visible events

**Started:** 2026-11-18
**Branch:** `fix/featured-cap-visible-only`, from `origin/uat` at `07db5ef` (after PR #96)
**One-line description:** The "up to 3 featured events" cap counted every flagged, unexpired event, including completed and cancelled ones, but the homepage only shows `on_sale` and `sold_out` events. Nothing clears the flag when an event completes, so stale completed events held all three slots: the hero was empty and an admin could not feature a new event. The cap and the homepage query now build their filter from one shared helper, so the cap counts exactly what the homepage would show.
**Artifacts:** none (no routes, DTOs, schema, env or migration changes). One module-level helper, `visibleFeaturedWhere(now)`, in `apps/api/src/events/events.service.ts`.

## What changed for users
- An admin can feature a new event when the only flagged events left are completed, cancelled, draft or expired. Before, they got "The homepage supports up to 3 featured events. Disable one before adding another." while the homepage showed nothing.
- Three visible featured events (`on_sale` or `sold_out`, not past `featuredUntil`) still block a fourth, with the same 400 and the same message.
- The public featured list returns exactly what it did before.

## UAT checks before `uat` to `main`
1. With stale completed events still flagged, the **admin page itself will still refuse** to feature a new event while it shows 3 / 3 (see follow-up 1), so test the cap through the API (an admin `PUT /admin/events/:id` with `isFeatured: true`) or after the web follow-up ships. Do not report the admin screen as unblocked.
2. API check: with 3 visible featured events, an admin `PUT /admin/events/:id` that features a fourth is refused with the same 400 message as before.
3. API check: stale completed or cancelled events that still carry the flag do not count toward the cap.
4. `GET /api/v1/events/featured` still returns only `on_sale` / `sold_out` flagged events, at most three.

## Follow-ups (not in this PR)
1. **Web admin page has the same bug.** `apps/web/src/app/admin/featured/page.tsx` (lines ~288-289) computes `activeFeaturedCount` with only the `featuredUntil` test and no status filter, and `handleToggle` refuses client-side at `FEATURED_LIMIT`. After this API fix the page will still show "3 / 3 active slots" and the toast "The homepage supports up to 3 featured events. Disable one first." when completed events are still flagged. Fix: count only `on_sale` / `sold_out` there too. Until then the workaround is to switch the stale completed events off in the same page. Not touched here (brief said API only).
2. **Nothing clears `isFeatured` when an event completes or is cancelled.** This PR makes the stale flag harmless to the cap; it does not clean it up. Not needed for correctness, but the admin list keeps showing stale rows as featured.
3. **Accepted limitation (API gate finding 1, backend gate findings 1 and 2): the cap only runs when `isFeatured` flips from false to true.** Because drafts no longer count, an admin can flag several drafts and then publish them (status to `on_sale`) with no re-check, giving more than 3 eligible events; the homepage silently shows only 3 (`take: 3`, ordered by `featuredOrder` then `startsAt`). Platform-admin only, not a security issue, and the homepage stays capped. Same kind of gap that already existed: extending `featuredUntil` on an already-flagged event skips the check, and the count-then-update is not atomic, so two simultaneous saves can both pass. Options if it matters: re-run the cap when a flagged event moves into `on_sale` / `sold_out` (compute the resulting flag, status and `featuredUntil` in `update()` and check whenever the event becomes visible), and put the count and the write in a transaction with a `pg_advisory_xact_lock` in the style already used at `events.service.ts` ~739 and ~770 (needs the rule 5 waiver decision above); or accept `take: 3` as the backstop. **Ship this with follow-up 1, or in order:** once the web count is aligned with the server rule, this becomes reachable from the admin screen (today the web count, which still counts every flagged event, masks it).
4. Production is probably affected in the same way (unverified: no database access from this session). The next `uat` to `main` promotion fixes it without any data change.
