1. Security Philosophy

  • Defense in depth: Multiple layers of controls — validation at API boundaries, authorization on every handler, signed URLs for private assets.
  • Least privilege: Admin access is all-or-nothing at MVP (single admin). Attendee session tokens are scoped to a single registration.
  • No security by obscurity: QR tokens are cryptographically random (UUID v4) — not sequential IDs. Proof URLs are server-signed — not guessable.
  • Fail secure: Unknown tokens → deny. Invalid MIME → reject. Expired signatures → deny. Missing JWT → 401.
  • Privacy by design: No PII in logs, QR payloads, or Cloudinary metadata. Email addresses normalized and stored — not echoed in public URLs.

6. File Upload Security

MIME Type Validation (Magic Bytes)

File TypeMagic Bytes (Hex)Offset
JPEGFF D8 FFBytes 0–2
PNG89 50 4E 47 0D 0A 1A 0ABytes 0–7
PDF25 50 44 46 (%PDF)Bytes 0–3

Upload Security Controls

  1. Size check first: Content-Length header checked before reading body. Files over 5MB rejected with HTTP 413 before any processing.
  2. Magic byte check: Buffer read from the first 8 bytes. If not matching any approved signature → HTTP 400 "Invalid file type."
  3. Extension not trusted: A .jpg extension with a PDF magic byte header is still accepted as PDF and labelled correctly. A .exe with MZ header is always rejected.
  4. Cloudinary private upload: type: 'private' means no public URL is accessible. The Cloudinary CDN serves the file only via authenticated signed URLs.
  5. Upload rate limit: 5 proof uploads per registrationId per hour (Redis counter). Prevents storage abuse.
  6. Filename sanitization: Original filename not used in storage key. Cloudinary generates its own public_id. No filesystem access on the server.

What is NOT accepted

  • HTML, XML, SVG (could contain script tags or XXE)
  • GIF (could contain script in metadata or pixel injection in historical exploits)
  • ZIP, RAR, or any archive (could contain path traversal payloads)
  • Any file where magic bytes don't match approved signatures

7. Payment Proof Privacy (Signed URLs)

How Signed URLs Work

  1. Proof image is uploaded to Cloudinary with type: 'private'.
  2. Only the publicId (e.g., axon-tickets/proofs/reg_01/proof_01) is stored in the database — NOT the full URL.
  3. When an admin opens the verification detail page, the frontend calls GET /api/v1/admin/verifications/:id/proof-url.
  4. The API verifies the admin JWT, then calls cloudinary.utils.private_download_url(publicId, 'jpg', { expires_at: now + 1800 }).
  5. The signed URL (with HMAC signature in query params, expiry timestamp) is returned to the frontend.
  6. The frontend renders the image using this URL directly. The URL expires after 30 minutes.
Never: Return a raw Cloudinary URL for a proof image. Never store the full URL in the DB as a directly-accessible link. If the admin accidentally shares the signed URL, it expires in 30 minutes and becomes useless.

8. IDOR Prevention

Registration-Level IDOR

  • Attendee session JWT payload: { sub: registrationId }.
  • Every endpoint that uses a :registrationId path parameter MUST verify: request.user.sub === params.registrationId.
  • This check is implemented as a Guard decorator (@OwnRegistrationGuard()) applied to all attendee-facing routes.
  • Example: if attendee A has token for registration X, they cannot access GET /registrations/Y even if they guess Y's ID.

Proof-Level IDOR

  • Proof records are linked to a registrationId.
  • Admin can view any proof via the verification detail endpoint (admin JWT required).
  • Attendees cannot request signed proof URLs directly — that endpoint is admin-only.

Attendee-Level IDOR

  • An attendee session can only access their own registration — not individual attendee records of other people in the same group.
  • Group attendee emails are sent to each individual — the lead cannot view the personal details of co-attendees via the API (only their own registration summary).

9. Input Validation & Injection Prevention

API Validation (NestJS)

  • All request bodies validated via class-validator decorators on DTOs.
  • ValidationPipe with whitelist: true, forbidNonWhitelisted: true — extra fields stripped and rejected.
  • String fields: max length enforced (e.g., firstName max 100, city max 100, rejectionNote max 300).
  • Email fields: @IsEmail() with normalization (lowercase, trim).
  • Integer fields: @IsInt(), @Min(), @Max() enforced.
  • Enum fields: @IsEnum() — only valid enum values accepted.

Database Query Safety

  • All DB queries via Prisma ORM — parameterized queries only.
  • No raw SQL ($queryRaw) in any new module.
  • If $queryRaw is needed in future: use Prisma.sql tagged template literal, never string concatenation.
  • Search functionality uses Prisma contains with mode: 'insensitive' — safe for text search.

Frontend Input Safety

  • All user-supplied text rendered via React (auto-escapes HTML entities).
  • No dangerouslySetInnerHTML in any new components.
  • URL parameters (slugs, registration IDs) validated on receipt at the API before use in queries.

CORS Policy

  • API CORS: origin: [process.env.WEB_URL] — production web domain only. No wildcard.
  • Credentials: true (required for cookie/auth header flows).
  • Allowed methods: GET, POST, PATCH, DELETE.
  • Preflight cache: 24 hours.

TLS

  • TLS 1.2 minimum enforced by Vercel (TLS 1.3 preferred). Managed certificates via Vercel.
  • No self-signed certificates in any environment.

12. PII Handling & Data Privacy

What is PII in Axon Tickets

  • First name, last name, email address, contact number — all collected during registration.
  • Optional: gender, age, country, company, affiliation, city.
  • Payment proof screenshot (financial image — potentially contains bank account numbers, reference codes).

Data Minimization

  • Email addresses collected at registration — used for confirmation, QR delivery, rejection notices. Not used for marketing (MVP has no marketing module).
  • Optional fields (gender, age, country, etc.) collected only if provided — never required.
  • EventView logs store anonymous sessionId only — no email, name, or IP address.

Philippine Data Privacy Act (DPA) 2012 — MVP Compliance

  • Attendees provide consent at registration (registration form includes data collection notice).
  • Data used only for the stated purpose: event registration and attendance.
  • Data not shared with third parties beyond: Resend (email delivery — data processor), Cloudinary (image storage — data processor), Neon (database — data processor).
  • Attendee can request data deletion via organizer (no automated self-service deletion in MVP).

13. Audit Trail

Covered Actions (MVP)

  • CREATE_EVENT, UPDATE_EVENT, CANCEL_EVENT
  • CREATE_TIER, UPDATE_TIER, DELETE_TIER
  • APPROVE_REGISTRATION, REJECT_REGISTRATION, BULK_APPROVE
  • RESEND_QR, CHECKIN_MANUAL, CHECKIN_OVERRIDE
  • EXPORT_CSV

Audit Log Properties

  • Each entry is immutable (no UPDATE, no DELETE on AuditLog table).
  • Contains: adminId, action, entityType, entityId, metadata (structured JSON), createdAt.
  • No PII in metadata — only IDs, reason codes, counts.
  • Retention: all records kept for MVP. Post-MVP: 1-year rolling delete recommended.

14. Dependency & Supply Chain Security

  • Run npm audit before every production deployment. Critical or high severity findings must be resolved before deploy.
  • Lock file (package-lock.json) committed to repo — prevents dependency version drift.
  • No --force installs that bypass peer dependency warnings without review.
  • New dependencies must be justified and reviewed before adding (principle of minimal dependencies).
  • Cloudinary SDK, Resend SDK, and Prisma are pinned to specific minor versions.
  • Post-MVP: Dependabot alerts configured on GitHub repository for automatic vulnerability notifications.
