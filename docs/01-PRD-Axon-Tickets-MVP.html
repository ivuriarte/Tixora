1. Executive Summary

Axon Tickets is a responsive web-based event registration and attendance platform designed for the Philippine market. The MVP focuses on operational excellence: smooth mobile-browser registration, manual payment verification via QR/bank transfer, individual QR code delivery per attendee, and event-day check-in. The platform serves multiple concurrent events and is designed to scale from small fun runs (100 participants) to professional conferences (500+ participants).

The long-term vision is an event engagement and attendee intelligence platform with behavioral analytics, targeted marketing, and organizer intelligence. The MVP deliberately focuses on operational reliability first — the foundation must be trustworthy before marketing is layered on top.

Platform Scope Clarification: Axon Tickets is a responsive web application only. There is no native iOS or Android application in scope. Mobile experience is delivered via the same web application using responsive layouts, mobile-first CSS, and browser-native camera access for QR scanning.

2. Problem Statement

The Organizer's Problem

  • Event organizers in the Philippines collect payments manually (GCash, bank transfer) but have no structured system to verify and track these payments.
  • Proof of payment arrives via chat (Messenger, Viber, email) — unstructured, hard to track, easy to lose.
  • Generating and distributing QR codes or tickets after payment verification is done manually and is highly error-prone.
  • Event-day check-in relies on printed lists, screenshots, or manual spreadsheet lookups — slow and frustrating.
  • Group/corporate registrations (where one person pays for multiple) require tracking individual attendees — current tools don't support this.

The Attendee's Problem

  • No clear status visibility after registering — "Did they receive my payment? Am I on the list?"
  • Registration anxiety: attendees are unsure if their name is confirmed, especially for group entries.
  • QR code delivery is inconsistent — sometimes via chat, sometimes email, often late or missing.
  • Registration flows for Philippine events are not optimized for mobile browsers — desktop-first forms that are hard to use on a phone.

4. User Personas

ATTENDEE Maria — The Mobile Registrant

Background: 28-year-old professional, uses smartphone (Android) daily. Registers for fun runs, talks, and corporate events. Tech-comfortable but not technical.

Behavior: Discovers events via social media or organizer invite. Registers on her phone during lunch break or commute. Pays via GCash immediately. Forgets to check email regularly.

Needs: Fast mobile form, clear payment instructions, confidence that her name is on the list, QR code in her inbox before event day.

Frustrations: Long forms on mobile, unclear payment status, not knowing if payment was received, forgetting where she saved the QR code.

Goals: Register quickly, pay easily, arrive on event day without stress.

ATTENDEE Carlo — The Group Coordinator

Background: HR officer at a mid-size company. Coordinates team attendance for corporate events, fun runs, and talks. Registers 5–10 people at once.

Behavior: Collects colleague info (names, emails, contact numbers) before registering. Pays one amount for the whole group. Expects each colleague to receive their own QR code.

Needs: Group registration form, single payment, individual QR delivery to each email, confirmation that all names are registered.

Frustrations: Having to register each person separately, unclear bundle pricing, no confirmation per attendee.

ORGANIZER / ADMIN Ana — The Event Organizer

Background: Event coordinator, manages 2–5 events per year. Uses desktop/laptop for planning, phone for event-day operations.

Behavior: Creates events weeks in advance, reviews payment proofs daily during registration period, handles event-day check-in personally or delegates to a colleague.

Needs: Clear pending verification queue, fast approve/reject with one click, bulk-friendly workflow, reliable QR email delivery, event-day QR scanner on mobile browser.

Frustrations: Hunting for payment proof screenshots in chat, manually sending QR codes, spreadsheet-based attendee tracking, duplicate entries.

Goals: Manage registrations with minimal repetitive work, have confidence in attendance data, deliver a professional experience to attendees.

6. Authentication Model

Design Decision: Axon Tickets follows the airline model (PAL / Cebu Pacific) for attendee access — no mandatory account creation. Attendees access their registration using their email address + registration reference number. This eliminates friction for mobile registrants and is appropriate for a 300–450 person event.

Attendee Authentication Flow

  1. Attendee submits registration → system creates record → sends confirmation email containing the registration reference number (e.g., AXN-20260619-0042).
  2. To check registration status: attendee visits the platform → enters email + reference number → gains access to their registration page.
  3. Session persists for 24 hours (inactivity-based timeout).
  4. After accessing their registration, attendee may optionally complete their profile (password setup, additional details) to enable standard email/password login in future.

Organizer Authentication Flow

  1. Organizer uses standard email + password login.
  2. JWT access token (15-min TTL) + refresh token (7-day TTL).
  3. All admin routes protected by JwtAuthGuard + AdminGuard.
  4. Brute-force protection via Redis (max 5 failed login attempts before lockout).

Profile Completion (Post-Registration)

  • After accessing via email + reference, attendees see an optional "Complete your profile" prompt.
  • Optional fields: password (to enable future login), phone, company, affiliation, city, gender, age, country.
  • Not required to access QR code or check registration status.

Group Registration

  • Lead registrant fills in their own details first (same fields as solo).
  • "Are you registering for others?" toggle reveals additional attendee rows.
  • Each additional attendee row: First Name, Last Name, Email, Contact Number (all required per row).
  • Maximum attendees per bundle: 10 (default). Configurable per event by admin (e.g., set to 5 for controlled events).
  • 1 QR code generated per attendee upon approval.
  • Each attendee's QR is sent to their individual email address.
  • One payment proof covers the entire bundle.
  • Bundle pricing is set at the tier level (e.g., "Group of 5 — ₱1,500").

Duplicate Prevention

  • Per-event, per-email duplicate check: one active registration per email address per event.
  • A registration is considered "active" if its status is not cancelled.
  • Duplicate attempt returns: "This email address is already registered for this event. If this is unexpected, contact the organizer."
  • Group registration: each attendee email in the bundle is individually checked for duplicates.

Registration Reference Number

  • Format: AXN-YYYYMMDD-XXXX (e.g., AXN-20260619-0042)
  • Auto-generated on registration creation.
  • Globally unique.
  • Included in all emails and on the confirmation page.
  • Used as one of two credentials for attendee access (email + reference).

  • A scheduled job runs daily (or at tier sale end time).
  • Any registration in draft status for an expired tier (past saleEndsAt) is automatically transitioned to cancelled.
  • Cancellation email is sent to the attendee: "Your Early Bird registration has been cancelled as the registration window has closed. Please check if other ticket categories are available."

8. Payment Requirements

Payment Methods — MVP

  • GCash QR code (image uploaded by organizer per event)
  • Bank-generated QR code (image uploaded by organizer per event)
  • Organizer may upload one or multiple payment QR images per event.
  • Payment instructions are displayed on the payment screen.

Organizer Payment Setup (per event)

  • Admin uploads 1 or more payment QR images when creating/editing an event.
  • Each QR has a label (e.g., "GCash", "BPI Bank Transfer").
  • Optional: text instructions (e.g., account name, account number for manual transfer reference).
  • Attendees see the QR image and scan it in their banking app or GCash to pay.

Proof of Payment Upload

  • Accepted file types: image/jpeg, image/png, application/pdf
  • Maximum file size: 5MB
  • Validation: MIME type checked server-side against file magic bytes (not just extension)
  • Storage: Private Cloudinary folder — not publicly accessible
  • Access: Organizer accesses via time-limited signed URL (30-minute expiry)
  • Re-upload: Allowed after rejection. Re-upload replaces the previous proof record and transitions status back to submitted.

Payment Status Communication to Attendee

9. Organizer Requirements

Verification Queue

  • Default view: registrations with status submitted or pending_verification, sorted by submission time (oldest first).
  • Tabs: Pending | Approved | Rejected | All
  • Each row shows: Reference number, attendee name, tier, registration type (solo/group), attendee count, submission time, thumbnail of proof.
  • Click row → opens detail page with full-size proof image and full attendee details.

Approve Action

  • One-click approve on queue row or detail page.
  • Confirmation dialog: "Approve this registration and send QR codes to all attendees?"
  • On confirm: status → approved; QR tokens generated (1 per attendee); emails dispatched; audit log written.

Reject Action

  • Click Reject → modal with reason selector.
  • Preset reasons: "Incorrect amount", "Blurry / unreadable image", "Wrong payment reference included", "Duplicate payment proof", "Payment appears cancelled / reversed", "Other".
  • If "Other": free-text field (max 300 characters).
  • On confirm: status → rejected; rejection email sent with reason; audit log written.

Bulk Approve

  • Multi-select checkbox on queue (max 20 per bulk action).
  • Confirmation dialog lists all selected registrations before proceeding.
  • Each is individually approved (no partial failures — if one fails, it stays pending with error flag).

Admin Group Size Configuration

  • When creating or editing an event, admin sets maxGroupSize (default: 10, minimum: 2, maximum: 50).
  • This limit is enforced on the registration form and API.

Resend QR

  • Available on approved registration detail page.
  • Resends QR email(s) to all attendees in the registration.
  • Action logged in audit trail.

Audit Trail

  • All organizer actions are logged: create event, update event, approve registration, reject registration, resend QR, check-in override, bulk approve.
  • Each log entry: admin user ID, action type, entity type (event/registration/attendee), entity ID, metadata (rejection reason, etc.), timestamp.
  • Audit log is MVP-included (not future state).
  • Admin can view audit log on a dedicated page filtered by action type or date range.

10. QR & Attendance Requirements

QR Code Generation

  • One QR code per attendee (per person in the bundle, not per registration).
  • QR payload: opaque random token (UUID v4 or HMAC-signed) — no PII embedded in QR.
  • Tokens are unique and non-sequential.
  • QR image rendered as PNG and embedded in email.

Email Delivery

  • Each attendee receives their own individual email with their own QR code.
  • Email contains: attendee name, event title, event date/time, venue, Google Maps link, tier name, QR code image, registration reference.
  • Email is triggered automatically on organizer approval.

Check-in (Event Day)

  • Primary: Browser camera QR scanner on /admin/checkin — optimized for mobile browser.
  • Secondary: Manual token paste/type (existing functionality retained).
  • Tertiary fallback: Search attendee by name or email.
  • Check-in result: attendee name, tier, check-in timestamp, success/already-checked-in/invalid state.
  • Duplicate check-in: returns "Already checked in at [time]" — does not re-check-in.
  • Only tickets from approved registrations can be checked in.

12. UX & Design Requirements

Design Philosophy

  • Apple-inspired: Clean, purposeful, generous whitespace, rounded forms, no decorative clutter.
  • Mobile-first: All attendee flows designed for 375px mobile viewport first, then expanded for desktop.
  • Calm confidence: Professional without being intimidating. Welcoming without being playful.
  • Always show next step: Every screen tells the user what to do next. No dead ends.

Typography

  • Font: Inter (existing — retain)
  • Base size: 16px (1rem) on mobile, 15px on desktop
  • Line height: 1.6 for body text
  • Headings: Bold, dark navy (#1A3A5C)

UX Rules

  1. Submit buttons disabled until all required fields are valid.
  2. Inline field-level error messages (not toast-only).
  3. Every form submission triggers a clear confirmation state (not just a toast).
  4. Never redirect attendee away from the app to complete registration (no PayMongo redirect in MVP).
  5. Group registration rows must be collapsible on mobile (accordion pattern).
  6. File upload shows progress indicator, then a clear success/failure state.
  7. Organizer verification queue must be keyboard-navigable (Tab + Enter to approve/reject).
  8. Check-in scanner must render full-screen on mobile with large result cards.
  9. No pagination that requires multiple page loads for < 450 records — use virtual scroll or single-page pagination.

14. Assumptions & Constraints

Assumptions

  • The initial events will use GCash QR or bank-generated QR as payment methods. No cash or other methods for MVP.
  • There is one admin account for MVP. Multi-admin support will be added in a future phase.
  • All events are in the Philippines (Philippine Peso, Asia/Manila timezone).
  • Attendees have access to a mobile browser with camera support for QR scanning.
  • Resend transactional email is configured with a verified custom domain before production launch.
  • Cloudinary is configured for both event images (existing) and payment proofs (private folder, new).
  • The platform hosts multiple concurrent events (not single-event only).
  • Registration design assets (logo, brand colors, event posters) will be provided before production launch.
  • Group registration maximum of 10 per bundle is sufficient for MVP. Admin can adjust per event.
  • Proof re-upload after rejection is allowed. Original proof is retained in audit trail but superseded.

Constraints

  • Budget: MVP must use free or low-cost tiers of all third-party services (Vercel, Neon/Supabase, Cloudinary, Resend).
  • Team: Single development team — phases must be sequential and non-overlapping.
  • Timeline: TBD — no hard deadline set, but events begin in June 2026 (Early Bird window).
  • Deployment: Vercel (web + API) + Neon PostgreSQL (existing setup must be preserved).
  • No breaking changes to existing schema unless absolutely necessary — additive migrations preferred.
