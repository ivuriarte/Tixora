WHAT ARE WE BUILDING?

Tixora is a modern online ticketing platform for events in the Philippines. It allows customers to browse events, buy tickets, receive QR codes, and attend events — while giving organizers tools to manage everything from ticket inventory to check-in at the door.

Two Sides of the Platform

SideWho Uses ItWhat It Does
Customer AppTicket buyersBrowse events, buy tickets, receive QR codes, view "My Tickets"
Admin DashboardEvent organizers & staffCreate events, manage inventory, scan QR codes at the door, view analytics

Core Problem We're Solving

  • Overselling — Two people cannot buy the last ticket. The system prevents this at the database level.
  • Scalpers & bots — Automated programs cannot bulk-buy tickets. Rate limiting, CAPTCHA, and purchase limits stop them.
  • Poor mobile experience — Most ticket buyers in PH are on mobile. The entire system is mobile-first.
  • Slow, clunky checkout — A frictionless 5-step checkout with a clear countdown timer and simple payment flow.

What Tixora Is NOT (MVP Scope Cuts)

FeatureStatusReason
Seat maps / reserved seatingNot in MVPComplex, not needed for initial events
SMS OTPNot in MVPEmail OTP is sufficient; SMS adds cost and carrier complexity
Full refund automationNot in MVPManual process for MVP, automate in v2
Ticket transfer between usersNot in MVPv2 feature
WaitlistNot in MVPv2 feature
Native mobile appNot in MVPPWA (mobile browser) covers this

Why separate frontend and backend? During a ticket drop, thousands of users hit the site at once. Having a separate API server means you can handle the traffic surge on the backend without affecting the frontend. Vercel's global CDN serves the frontend from edge nodes near users — the heavy load goes to the Railway backend.

2.3 Database Schema

All tables use UUIDs as primary keys. The schema enforces data integrity at the database level — not just application level. The sold_quantity <= total_quantity constraint on ticket tiers is the last line of defense against overselling.

Core Tables

eventsEvents for saleslug, title, venue, starts_at, status, max_per_user
ticket_tiersTicket types per event (GA, VIP, etc.)price, total_quantity, sold_quantity, max_per_order, sale_starts_at
reservationsTemporary holds (10-min TTL)user_id, tier_id, quantity, expires_at, status, idempotency_key
ordersConfirmed purchasesuser_id, status, total, payment_method, payment_ref, ip_address

Critical Database Constraints

-- Prevents overselling at the database level (last line of defense)
CONSTRAINT sold_lte_total CHECK (sold_quantity <= total_quantity)

-- Enforced on ticket_tiers table
-- Even if application code has a bug, the DB will reject the update

-- Idempotency keys prevent double-submissions
UNIQUE constraint on reservations.idempotency_key
UNIQUE constraint on orders.idempotency_key
UNIQUE constraint on tickets.qr_code

-- Cascade deletes keep data clean
ticket_tiers → ON DELETE CASCADE when event is deleted
order_items  → ON DELETE CASCADE when order is deleted

2.5 Ticket Inventory Strategy

This is the most critical system in the entire platform. Overselling tickets destroys trust and creates legal liability. The dual-layer approach below makes overselling essentially impossible.

Phase 1 — Reservation (Redis — Fast Path)

When user clicks "Reserve":
  1. Verify hCaptcha token
  2. Check user's active reservation count < 3
  3. Check user has not hit max_per_user for this event
  4. Redis: DECRBY ticket_tier:{id}:available by quantity
     → If result < 0: INCRBY back → return 409 "Sold Out"
     → If result ≥ 0: proceed
  5. Write reservation row to PostgreSQL (expires_at = NOW() + 10 min)
  6. Return { reservation_id, expires_at, subtotal } to client
  7. Client starts countdown timer

Phase 2 — Order Confirmation (PostgreSQL — Source of Truth)

When user completes payment:
  BEGIN TRANSACTION;
    -- Lock the reservation row (no other transaction can touch it)
    SELECT * FROM reservations
    WHERE id = $1 AND status = 'active' AND expires_at > NOW()
    FOR UPDATE;

    -- Deduct inventory with constraint enforcement
    UPDATE ticket_tiers
    SET sold_quantity = sold_quantity + $qty
    WHERE id = $tier_id
      AND (sold_quantity + $qty) <= total_quantity;

    -- If 0 rows affected → oversell attempt → ROLLBACK

    INSERT INTO orders ...;
    INSERT INTO order_items ...;
    UPDATE reservations SET status = 'converted';
  COMMIT;

Reservation Expiry (Cron Job)

Every 60 seconds:
  SELECT * FROM reservations WHERE status = 'active' AND expires_at < NOW();
  For each expired reservation:
    → INCRBY ticket_tier:{id}:available (restore to Redis)
    → UPDATE reservation SET status = 'expired'

Two users race for the last ticketOne gets the atomic decrement; the other gets -1 and is immediately rejected with "Sold Out"
User takes 8 minutes to payReservation TTL is 10 minutes — covers processing time
User abandons checkoutCron job reclaims expired reservation after 10 minutes
Same form submitted twiceidempotency_key — second request returns the first order, no duplicate created

4.1 Authentication Flow

StepActionTechnical Detail
1User registersPOST /auth/register — password hashed with bcrypt (cost=12)
2OTP sent6-digit code, 5min TTL, stored hashed in Redis + DB, sent via Resend
3User verifies emailPOST /auth/verify-email — compare OTP hash, mark user verified
4Tokens issuedJWT access token (RS256, 15min) + refresh token (64-byte random hex, 7 days)
5Refresh token storedHashed in Redis, sent as HttpOnly Secure SameSite=Strict cookie
6Access token expiresPOST /auth/refresh — validate cookie, rotate both tokens
7LogoutDelete refresh token from Redis — all sessions invalidated

4.3 QR Check-In Flow

StepAction
1Admin opens check-in page on phone/tablet (camera access requested)
2Staff scans attendee's QR code
3POST /admin/checkin { qr_token }
4Server: verifyQRToken() — if signature invalid → 400 "Invalid QR"
5Server: SELECT ticket FOR UPDATE
6If status = 'used' → 409 "Already checked in" (prevents reuse)
7If status = 'valid' → UPDATE status='used', checked_in_at=NOW()
8Return { valid: true, attendee_name, tier_name } — green screen shown
