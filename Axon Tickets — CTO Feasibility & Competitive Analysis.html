LayerTechnologyRationale

DatabasePostgreSQL via SupabaseWhere all platform data lives — events, orders, attendee records, user accounts. Cloud-hosted with automatic daily backups and the ability to restore data to any point in time

How the platform is hosted: The platform runs entirely in the cloud with no physical servers to manage or rent. It automatically powers up when buyers visit and scales to handle high demand — such as a surge when ticket sales open — then scales back down, keeping costs minimal during quiet periods.

Section 05

Feasibility Assessment

DimensionRatingNotes
Can We Build It? High The platform works. The three core journeys a buyer takes — discovering an event, purchasing a ticket, and being scanned in at the door — have all been built and tested. No fundamental blockers remain.
Can We Afford to Run It? High Running costs are ₱0 while we build. At launch, total fixed monthly costs are approximately ₱4,060 — far below the revenue expected from even a single small event. The platform effectively pays for itself after the first event.
Can It Handle a Large Crowd? Medium The platform is built to handle sudden surges in visitors — such as when a popular event goes on sale and many buyers arrive at once. One planned database upgrade (₱1,450/mo) is needed before handling very large events to ensure nothing slows down.
Is Buyer Data Safe? Satisfactory A formal security review was completed using internationally recognised standards. All login sessions are encrypted, access requests are rate-limited to block abuse attempts, and no sensitive information is stored in the codebase. Buyer data is protected.
Can We Launch by July 2026? Medium 2–3 features are still in development: automatic email ticket delivery, buyer profile collection at checkout, and attendee list export. These are achievable within the timeline. No new features should be added before July — focus is critical.
Code Quality & Maintainability Low The codebase is consistently structured, uses automated checks to catch errors early, and is documented for readability. A second developer could be onboarded quickly without needing to rebuild or relearn the system from scratch.
Are We Locked Into Any Vendor? Low Every tool and service used can be replaced with an alternative if needed. The database, hosting provider, payment gateway, and email service are all standard, widely-used solutions — we are not locked into any proprietary system.

Section 07

Key Risks & Mitigations

Risk & Why It ExistsSeverityHow We Are Addressing It
Slow response during a ticket rush
When a popular event goes on sale, many buyers may try to purchase at the exact same second. Cloud functions need a brief moment to start up under heavy simultaneous load, which can cause short delays during peak traffic.		 Medium Seat reservation locks are applied immediately, so no double-booking can occur even during a rush. At current event sizes, any delay is imperceptible to buyers. This will be reviewed before any event with 1,000+ simultaneous visitors.
Payment gateway goes down during a sale
Like any online service, PayMongo can occasionally have outages. If this happens during an active ticket sale window, buyers will be unable to complete purchases — leading to missed revenue and frustrated attendees.		 Medium Stripe (a global payment processor) is integrated as a backup. A manual fallback is also documented — directing buyers to bank transfer or GCash QR with admin order confirmation for emergencies.
Database free-tier limits before launch
The current free database plan has limits on how many buyers can interact with it simultaneously. If many people try to check out at the same time, this cap could cause slowdowns or errors during peak moments.		 Low Upgrade to the paid database plan (₱1,450/mo) at least two weeks before the first event. This removes connection limits and ensures stable performance during peak ticket demand.
July 2026 deadline — 3 features still in development
Automatic email ticket delivery, buyer profile collection at checkout, and attendee list export are still being built. If any of these are not ready in time, organiser and buyer experience at the first event will be impacted.		 Medium All three features are scoped and in active development. No new feature requests should be added before July. An interim workaround — admin manually forwards tickets — exists for the first event if needed.
Single developer dependency
The platform is currently being built and maintained by one person. Any unexpected absence, illness, or overload could slow progress — especially critical as the July launch date approaches.		 Medium The codebase is structured and documented for team readability. A second developer can be brought in and productive quickly. All key decisions and deployment procedures are documented in the project repository.

CTO Recommendation: The platform is ready to launch. It is technically sound, financially efficient, and addresses a clear gap in the local market that no competitor currently fills. The only critical risk is time — three features must be completed before July 2026. Development effort should be fully focused on those deliverables. No new features should be introduced before the first event. July 2026 is the go / no-go milestone.
